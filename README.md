# doc-extractor

Извлечение реквизитов из текста входящих документов (счета, коммерческие предложения, акты) в JSON фиксированной схемы. Главная задача — не выдумывать то, чего в документе нет: локальная модель (Ollama) только предлагает значения, а детерминированный код подтверждает каждое из них по тексту документа; не найденное становится `null` с предупреждением ([ADR 0001](docs/adr/0001-text-grounding-after-llm.md)). Предупреждения пишет только код, не модель ([ADR 0003](docs/adr/0003-warnings-only-from-code.md)). Оценка качества по умолчанию воспроизводит записанные ответы модели, поэтому работает без Ollama ([ADR 0002](docs/adr/0002-eval-replays-recorded-responses.md)). Термины — в [GLOSSARY.md](GLOSSARY.md).

## Запуск с нуля

Нужны Python ≥ 3.11 (как в `pyproject.toml`) и `make`; на Debian/Ubuntu ещё пакет `python3-venv` (`sudo apt install python3-venv`). Виртуальное окружение создаёт сам `make install` (отдельный `python3 -m venv` не нужен).

```bash
git clone https://github.com/montedeu/doc-extractor.git
cd doc-extractor
make install
```

`make install` создаёт `.venv`, обновляет pip в нём (для `pip install -e .` нужен свежий pip) и ставит закреплённые зависимости. Без `make`: `python3 -m venv .venv && .venv/bin/python -m pip install --upgrade pip && .venv/bin/pip install -r requirements.txt && .venv/bin/pip install -e .`, а вместо `make eval` — `.venv/bin/python eval.py --mode replay`.

Ollama ([установка](https://ollama.com/download)) нужна только для живого извлечения (`extract`, `make eval-live`, `make record`); тесты и `make eval` обходятся без неё:

```bash
ollama pull qwen3.5:9b          # модель по умолчанию, ≈6.6 ГБ (по `ollama list`)
ollama pull qwen3.5:4b          # быстрее (≈вдвое, см. оговорку о замерах ниже), но менее точная
export DOC_EXTRACTOR_MODEL=qwen3.5:4b   # выбрать другую модель (по умолчанию qwen3.5:9b)
```

## Использование

```bash
.venv/bin/python -m doc_extractor extract data/docs/doc_01.txt
cat data/docs/doc_01.txt | .venv/bin/python -m doc_extractor extract -
```

stdout — только JSON результата, сообщения для человека — в stderr. Пример результата для `data/docs/doc_01.txt` — это воспроизведение записанного ответа `qwen3.5:9b` через весь пайплайн (`ScriptedClient`), а не живой запуск; живой запуск может отличаться (модель недетерминирована между версиями):

```json
{
  "doc_type": "invoice",
  "supplier_name": "ТОО \"Алматы Трейд Компани\"",
  "supplier_bin": "170340021554",
  "doc_number": "1245",
  "doc_date": "2026-11-12",
  "currency": "KZT",
  "total_amount": 186180.0,
  "vat_amount": 25680.0,
  "line_items": [
    {"name": "Бумага А4 80г/м2", "qty": 50.0, "price": 2100.0},
    {"name": "Картридж HP 85A", "qty": 3.0, "price": 18500.0}
  ],
  "field_confidence": {
    "doc_type": 1.0, "supplier_name": 1.0, "supplier_bin": 0.5, "doc_number": 1.0,
    "doc_date": 1.0, "currency": 1.0, "total_amount": 1.0, "vat_amount": 1.0, "line_items": 1.0
  },
  "warnings": ["bin_checksum_failed: supplier_bin=170340021554"]
}
```

(В реальном выводе JSON печатается с отступами; здесь строки свёрнуты.) БИН в этом документе записан как в тексте, но контрольная цифра не сходится — поэтому предупреждение и уверенность 0.5.

| Код | Когда |
|---|---|
| 0 | результат получен (поля могут быть `null`, предупреждения — быть) |
| 1 | ошибка ввода: файла нет, не UTF-8; stdout пуст |
| 2 | пустой результат: два ответа модели подряд не прошли валидацию; результат (с `validation_failed`) в stdout |
| 3 | Ollama недоступна или модель не скачана; stdout пуст, в stderr готовая команда |

## Тесты и eval

```bash
make test        # pytest, модель не нужна
make eval        # отчёт по записанным ответам, без Ollama
make eval-live   # то же, но живая модель (нужна Ollama)
make record      # перезаписать ответы модели в results/responses/<модель>/
```

`make eval` по умолчанию воспроизводит записанные ответы `qwen3.5:9b` (`results/responses/`, ADR 0002): проверяющему не нужны Ollama и ≈6.6 ГБ модели, а живая модель недетерминирована между версиями. Записан сырой ответ модели (включая невалидные и повторные); валидация, повтор, сверка с текстом, поиск противоречий и метрики исполняются по-настоящему. После любого изменения промпта или схемы ответы устаревают: `eval.py` сравнивает хеш `prompt.py` и предупреждает, тогда нужен `make record`. Другая модель: `DOC_EXTRACTOR_MODEL=qwen3.5:4b make eval` (записи для неё тоже лежат в репозитории). Полный отчёт по документам сохраняется в `results/eval_report.json`. Тестовый набор — 10 документов `data/docs/`, эталоны — `data/gold/`.

## Результаты

Тестовый набор: 10 документов. Исход поля: верно / галлюцинация (эталон `null`, у нас значение) / пропуск / неверно (оба заполнены, не равны). Строка ИТОГО; у каждой строки свой знаменатель (сумма исходов), потому что лишняя позиция (галлюцинация `line_items.name`) добавляет сравнение, а недостающая — пропуск.

| Конфигурация | верно | галлюц. | пропуски | неверно | точность | предупреждения совпали | время на документ |
|---|---|---|---|---|---|---|---|
| (а) `9b`, первый промпт, без сверки (источник — PR #15, файла отчёта нет) | 115 | 2 | 11 | 2 | 88% | — | — |
| (б) `9b`, промпт с правилами спецификации (#16), без сверки (`results/baseline_report.txt`) | 120 | 2 | 7 | 1 | 92% | 6 из 10 | — |
| (в) `qwen3.5:9b`, итоговый промпт + сверка (`results/report_qwen3.5_9b.txt`) | 126 | 0 | 1 | 1 | 98% | 10 из 10 | ≈126 с |
| (в) `qwen3.5:4b`, итоговый промпт + сверка (`results/report_qwen3.5_4b.txt`) | 118 | 0 | 7 | 3 | 92% | 6 из 10 | ≈57 с |

**Время на документ** — один холодный прогон `make record` (wall clock: `9b` 1257 с, `4b` 568 с на 10 документов) на CPU-машине с MX250 2 ГБ; `ollama ps` показал `9b` на 98% CPU / 2% GPU. Замеров в репозитории нет, источник — PR #28. Предварительный замер на прогретой модели был 61 и 40 с на документ, так что цифры выше — верхняя оценка.

Остаточные ошибки `9b`: `doc_02` — пропущено название поставщика; `doc_03` — тип `act` вместо `invoice`. У `4b` — 7 пропусков (`supplier_name`: `doc_07`, `doc_10`; `supplier_bin`: `doc_03`, `doc_08`; `total_amount`: `doc_05`; `qty` и `price`: `doc_08`) и 3 «неверно» (`doc_type`: `doc_03`; `supplier_name`: `doc_04` — «ООО…» вместо «ТОО…», `doc_08` — «ЖШС…» вместо «ТОО…»).

**Модель по умолчанию — `qwen3.5:9b`.** Галлюцинаций нет у обеих, но `9b` точнее (98% против 92%) и единственная даёт верные предупреждения на всём наборе (10 из 10 против 6 из 10); `4b` быстрее (≈вдвое — с оговоркой о замерах выше), но чаще пропускает значения. Для документооборота, где пропуск лучше выдумки, но всё же стоит оператору времени, выбрана точность. `4b` остаётся вариантом, если важнее скорость: `DOC_EXTRACTOR_MODEL=qwen3.5:4b`.

Что стоит учитывать при чтении цифр:
- Правило промпта «наименование позиции — без количества, цены, суммы и валюты» добавлено после того, как на `doc_02` модель вписала цену в наименование. Формулировка общая, без цитат из набора, но это подстройка под тестовый набор: 100% по позициям на нём не доказывает того же на новых документах.
- Набор из 10 документов мал: один документ — 10 п. п. в точности поля, различие между моделями на отдельных полях статистически слабо.
- Замена «ЖШС → ТОО» и распознавание латинского «TOO» обеспечиваются только промптом, кодом не нормализуются; `4b` этому правилу не следует (`doc_08` «ЖШС…», `doc_04` «ООО…»).

## Правила и толкования

- **Итог** — «Всего к оплате» / «Итого к оплате», иначе «Итого». Если в документе есть другая, отличающаяся сумма к оплате — предупреждение `conflicting_totals`, поле получает уверенность 0.5.
- **Дата** — дата составления документа. Срок оплаты и срок действия предложения не используются. Две разные даты составления — предупреждение `conflicting_dates`.
- **Прописью vs цифрами** — это правило промпта (при расхождении брать цифры); код только предупреждает `amount_words_mismatch`. Числительные прописью на русском и казахском код понимает при сверке (итог, указанный только прописью, принимается).
- **НДС:** явное «без НДС» / «не облагается» → `0`; молчание → `null`; посчитанный самой моделью НДС → `null`.
- **БИН.** OCR-исправление букв (`O→0`, `l→1`) принимается, если контрольная цифра сходится (`ocr_corrected`); несходящаяся контрольная цифра без OCR — значение как в тексте с предупреждением `bin_checksum_failed`; OCR-кандидат с несходящейся цифрой — `null` с `bin_checksum_failed`. ИИН (у ИП) и БИН покупателя не считаются БИНом поставщика → `null` (`bin_not_supplier`). Комбинированная метка «БИН/ИИН» поддерживается.
- **Валюта** — только по маркеру в документе (₸, тг, тенге, KZT, $, USD, EUR…); без маркера `null`.
- **Позиции** — в порядке документа; позиция с ненайденным по тексту названием удаляется (`line_item_dropped`).
- **Название поставщика** — с организационно-правовой формой; для двуязычного — русский вариант целиком с русской формой (ЖШС → ТОО). Это правило промпта.

**Что ловит сверка с текстом и чего не ловит.** Ловит выдуманное: номер, дату, БИН, суммы, название, позиции, которых нет в нормализованном тексте. Не ловит перепутанное: «Итого» вместо «Всего к оплате» или срок оплаты вместо даты документа проходят сверку — их видит только eval (исход «неверно»). Малые числа (количество 1, 2, 3, НДС «0») слабо проверяемы: такая цифра почти всегда где-нибудь есть в тексте. `doc_type` не сверяется: это классификация.

**Уверенность полей (`field_confidence`).** 1.0 — значение найдено в тексте как есть; 0.7 — найдено после OCR-исправления; 0.5 — значение найдено, но с предупреждением (несходящаяся контрольная цифра, участие в противоречии). Поле, обнулённое сверкой, в словарь не попадает (ключа нет). Для `line_items` берётся минимум по позициям; 0.5 получает и `line_items`, если у позиции сверка обнулила `qty` или `price`. Это не оценка модели, а статус проверки.

## Что показывает отказ валидации

Если ответ модели не прошёл схему, пайплайн один раз повторяет запрос с текстом ошибки; если и повтор невалиден, возвращается пустой результат с `validation_failed`, а код выхода — 2. Воспроизвести без Ollama можно подставным клиентом:

```bash
.venv/bin/python -c "
from doc_extractor.llm import ScriptedClient
from doc_extractor.cli import main
raise SystemExit(main(['extract', 'data/docs/doc_01.txt'], ScriptedClient(['{', '{'])))"
```

Вывод (код выхода 2; текст ошибки pydantic сокращён):

```json
{
  "doc_type": "unknown", "supplier_name": null, "supplier_bin": null, "doc_number": null,
  "doc_date": null, "currency": null, "total_amount": null, "vat_amount": null,
  "line_items": [], "field_confidence": {},
  "warnings": ["validation_failed: 1 validation error for ModelAnswer Invalid JSON: EOF while parsing ..."]
}
```

То же в автотесте `test_validation_failure_exits_2_with_empty_result`. Недоступная Ollama — код 3 и подсказка (`OLLAMA_HOST=http://127.0.0.1:1 .venv/bin/python -m doc_extractor extract data/docs/doc_01.txt`).

## Ограничения эвристик

- Колоночные раскладки реквизитов (продавец и покупатель рядом, в две колонки) после превращения в текст перемешивают подписи и значения; метка БИН «ближайшая слева» может быть не той стороны.
- Мультивалютные и постраничные итоги: поддерживается одна валюта и один итог на документ.
- Казахские числительные в формах с окончаниями (падежи) распознаются не все.
- «Товарная накладная № … от» в шапке может дать ложные «две даты составления».
- Prompt injection: текст документа попадает в промпт. Сверка с текстом не даёт модели выдумать значение, но инструкция внутри документа может склонить её выбрать другое значение из того же документа; защиты от этого нет.
- Поддерживается только текст в UTF-8; сканы, PDF и OCR как этап не входят.
- Нормализация организационно-правовой формы (ЖШС, TOO, ООО → ТОО) — только в промпте, без кода.

## Сделано / не сделано / что дальше

Бюджет — 4 часа (старт 15:00, 19.11.2026). Решение разрабатывалось агентами по методу «Техлид»: спецификация — issue #1, реализация — тикеты #3–#12, #16, #17, #26 (PR #13–#15, #18–#25, #27–#29). Каждый PR прошёл code-review перед слиянием (см. разделы «Решения оркестратора» в телах PR), плюс два сводных ревью (`reviewer`).

**Сделано:** CLI с кодами выхода 0–3; схема и валидация с одним повтором; сверка с текстом по номеру, дате, БИН (контрольная цифра, OCR), суммам, НДС, валюте, названию, позициям; числительные прописью (ru, kk); поиск противоречий (итоги, прописью vs цифры, даты); `field_confidence`; eval с четырьмя исходами, записанными ответами и метрикой порядка позиций; сравнение `4b` и `9b`; ADR 0001–0003.

**Не сделано:** сканы и PDF; чтение таблиц с колонками; детерминированная нормализация организационно-правовой формы; защита от prompt injection; проверка на документах вне набора из 10 (метрики оптимистичны); пропускная способность для больших потоков (на CPU ≈126 с на документ для `9b`).

**Что дальше:**
1. Детерминированная нормализация ОПФ (ЖШС, TOO, ООО → ТОО) после модели, чтобы не зависеть от модели.
2. Расширить набор документов и эталонов, перезаписать ответы, пересчитать выбор модели.
3. Правила для колоночных раскладок, постраничных и мультивалютных итогов.
4. GPU-сервер или маленькая модель для потока; ограничение длины и экранирование документа в промпте.
